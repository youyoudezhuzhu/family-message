# 全局共享昵称系统 · 用户摘要

> 详细勘察与实施方案见 `docs/NICKNAME-SYSTEM-PLAN.md`。本文是精简版，读这一页就够。
> 状态：**已定稿（r6），未改任何代码**。默认值 / 占位符一律中性名（`LIVINGROOM-PC` / `客厅电脑` / `默认用户`）。
> **r6 六条口径**：① 昵称长度统一 **32**（NAS/API/PC/Web + 前端校验）；② PC 写操作走 **`/ws/device` 帧**（不新增 HTTP 写接口）；
> ③ ★**完全拒绝离线改昵称**（删掉整套 pending 机制）；④ ★★ `color` 存**逻辑色 ID**（显示色按主题算）；⑤ 活跃上限 **16** + 额度文案；⑥ **历史冻结 = 硬规则**（含「重创同名」不污染历史）。

## 1. 这个功能做什么

一句话：**昵称和昵称颜色改由 NAS 统一管理、全局共享** ——「妈妈 = 红色」在整个系统里只有**一个对象**，任何客户端（PC / 网页 / 将来的手机）都只是「**当前在用谁的名义**」发消息。新装客户端不预建任何昵称，第一次显示的是**灰色的本地临时昵称**。

## 2. 最终模型（三层状态）

```
  ┌───────── NAS：共享昵称池（唯一权威，唯一一张新表）─────────┐
  │  nicknames:  妈妈→color_12   爸爸→color_02   奶奶→color_05  │
  │           （昵称只存这里；color 是逻辑色 ID，不是 HEX）      │
  └─┬─────────────────┬──────────────────┬───────────────────┘
 广播↓+整表同步       ↓                  ↓ 广播
   客厅 PC(用:妈妈)   电脑浏览器(用:爸爸)   手机浏览器(用:没选)
     ↑ 各自的「当前昵称」只存在客户端本地
   灰临时昵称（旁路：不进池、不占色、不参与同步）
   默认用户 / LIVINGROOM-PC  +  逻辑色 `gray`  +  nickname_id = NULL
```

| 层 | 是什么 | 存在哪 | 谁能改 |
|---|---|---|---|
| ① 共享昵称 | 全系统唯一的「妈妈 → `color_12`」 | NAS 的 `nicknames` 表 | **任何客户端**（全是全局操作） |
| ② 当前使用昵称 | 这个客户端现在用谁的名义（也可以是「没选」） | **客户端本地**：PC 存配置，网页存本浏览器 `localStorage` | 只有这个客户端自己 |
| ③ 消息快照 | 这条消息**当时**的 id / 名字 / **逻辑色 ID** | `messages` 行内（入库存死） | 谁都不能改 |

② 为什么放客户端：Web 虽是公共端，但「一个浏览器 = 一份页面状态」。放服务端会出现「A 浏览器选了爸爸，把 B 的界面也改掉」——谁赢没有语义。代价：换浏览器要再选一次（清掉浏览器数据 = 回到「没选」= 灰色「默认用户」）。**服务端没有「当前昵称」端点。**

## 3. `nicknames` 表（完整 DDL，只有这一张新表）

```sql
CREATE TABLE IF NOT EXISTS nicknames (
    nickname_id  INTEGER PRIMARY KEY AUTOINCREMENT,
    display_name TEXT    NOT NULL CHECK (length(trim(display_name)) BETWEEN 1 AND 32),
    color        TEXT    NOT NULL CHECK (color IN (
        'color_01','color_02','color_03','color_04','color_05','color_06','color_07','color_08',
        'color_09','color_10','color_11','color_12','color_13','color_14','color_15','color_16')),
    status       TEXT    NOT NULL DEFAULT 'active' CHECK (status IN ('active','inactive')),
    created_at   TEXT    NOT NULL,
    updated_at   TEXT    NOT NULL
);  -- ★ r6：color 存「逻辑色 ID」（枚举 16 个），不再存 HEX

-- ① 一个 display_name 在活跃期只有一行（「同名只有一个对象」）；② 一个 color 在活跃期只属于一行（「不重色」）
CREATE UNIQUE INDEX IF NOT EXISTS ux_nicknames_name_active  ON nicknames(display_name) WHERE status='active';
CREATE UNIQUE INDEX IF NOT EXISTS ux_nicknames_color_active ON nicknames(color)        WHERE status='active';
```

- **只有这 6 列**：不许出现 `owner_type` / `owner_id` / `device_id` / `client_id`（归属字段已被禁止）。
- `nickname_id` 是**唯一身份**（永不变），`display_name` 只是**当前显示名**（可改）；名字 `1..32` 字符，**四端统一 32**。
- 两条都是 **partial unique index**（`WHERE status='active'`）：软删的行**不占位** → 删掉「妈妈」后可再建「妈妈」，颜色立即回池。
- ★ **活跃昵称上限 = 16**（颜色不重复的必然结果）。接近（`14/16`）提示「**共享昵称颜色即将用尽（14/16）**」；满 16 提示「**已达到共享昵称上限，请删除不再使用的昵称后再添加。**」并置灰新建入口；绕过 UI 直接请求仍是 503。
- **灰临时昵称不在这张表里**：它的逻辑色 ID 是 `gray`（基色 `#8A8A8A`），**不在那 16 个枚举里**，永远不分配给共享昵称。

## 4. 三个最容易混的操作

| 你想做什么 | 叫什么 | 影响面 | 存在哪 | 能离线做吗 |
|---|---|---|---|---|
| 我以后用「妈妈」的名义发消息 | **选择昵称** | 只影响**这个客户端** | 客户端本地（**一个字节都不上传**） | ✅ **能**（唯一能离线的） |
| 把「妈妈」改名叫「老妈」 | **修改昵称** | **全局**：所有用它的客户端一起变 | NAS，广播 `nickname_updated` | ❌ **不能** |
| 把「妈妈」的颜色换一个 | **重新分配颜色** | **全局** | NAS，广播 `nickname_color_changed` | ❌ **不能** |

- ★ **r6：四个管理操作（新建 / 改名 / 删除 / 重新分配颜色）全部必须在线** —— 离线时 UI 必须**禁用入口并明示原因**（例：「当前未连接服务器，昵称管理不可用」），**不排队、不本地生效、不生成 pending、不在重连时补发**。r4 / r5 的「离线 pending 昵称同步」**整套删除**。
- **新建 / 删除**与「修改昵称」同类：全局操作、必须在线；**「修改我这台 PC 的昵称」这件事不存在** —— PC 没有「自己的昵称」，它只是「当前用着某个共享昵称」。设置页不该有「本机昵称」输入框。

## 5. API 清单（**全部是全局操作**：家庭口令 + 可选 `nickname.manage`）

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/nicknames?status=active\|inactive\|all` | 列出昵称（**空表返回空数组，不创建任何东西**） |
| POST | `/api/nicknames` | 新建（服务端分配一个空闲**逻辑色 ID**）；撞名 → 409 `NICKNAME_ALREADY_EXISTS` + `existing_nickname_id`；池满 → 503 |
| PATCH | `/api/nicknames/{id}` | 改名（id 与颜色不变）；撞名 → 409 `NAME_TAKEN` |
| POST | `/api/nicknames/{id}/reassign-color` | 重新分配 = **换一个未被占用的逻辑色 ID**；池满 → 503 |
| DELETE | `/api/nicknames/{id}` | 删除（软删，**逻辑色 ID 立即回池**） |

- **选择昵称没有任何接口**（纯本地）；`GET` / `PUT /api/web/sender` 这类「服务端存当前昵称」的端点**不做**。
- PC 写操作走 `/ws/device` 帧（`nickname_list_request` / `nickname_create_request` / `nickname_rename_request` / `nickname_reassign_color_request` / `nickname_delete_request`）；**五个帧都必须在线**，**不进离线队列、不补发**。
- ★ **所有 `color` 字段都是逻辑色 ID**（`color_01`…`color_16` / `gray`），**协议里不出现 HEX**；请求体里**不接受任何颜色入参**。
- 广播只有**五个**：`nickname_created` / `nickname_updated` / `nickname_removed` / `nickname_color_changed` / `nickname_list_sync`（整表校正）。

## 6. 首次安装流程（一台新 PC / 一个新浏览器）

1. 读本机默认名：PC = `ComputerName`（如 `LIVINGROOM-PC`），网页 = 固定文案「默认用户」。
2. 向 NAS 拉整表：界面显示「当前昵称：`LIVINGROOM-PC` / 颜色：灰（`gray`）」——**NAS 什么都不做**（不建行、不分配颜色）。
3. 用户二选一：**方式 A 选用已有** → 只在本地记 `current_nickname_id`；**方式 B 新建** → 名字已存在 → 409，UI 提示「已存在，直接选用它？」。
4. 还没选也能发消息（灰临时昵称，见 §7）；但**断网时「新建」会直接不可用**（§4）。

## 7. 消息结构与表迁移

- 消息对外形状：`{message_id, nickname_id, nickname, color, content, created_at, direction}`，对应快照三字段 `nickname_id` + `display_name_snapshot` + `color_snapshot`；**`color` 是逻辑色 ID**（如 `"color_12"`，不是 HEX）。
- **`messages` 加两列**（可空）：`sender_nickname_id`（灰临时 = `NULL`）+ `sender_color`（当时的**逻辑色 ID**；灰 = `'gray'`）。`sender_name` 不动 —— **它就是名字快照**。
- ★ **读取时不 JOIN 昵称表**（硬规则：改名 / 改色 / 删除昵称，历史消息**原样显示**）；★ **重创同名（r6）**：删掉「妈妈」后再建一个「妈妈」= **新的一行、新的 `nickname_id`**；老消息仍指向**旧行**，显示**旧名字 + 旧逻辑色 ID**，不受任何影响。⇒ **`nickname_id` 绝不能按 `display_name` 去查**（否则老消息会被误挂到新行，历史集体变色）。
- ★ **存量回填：不做**（r6 定稿）。三条理由：① 老消息本来没有共享身份，回填是**编造**；② 回填的是「回填那一刻的颜色」，不是发送时的颜色；③ **与重创同名叠加会出错** —— `IS NULL` 只保证「已填过的行不改」，回填跑得越晚 / 越多次，越可能把老消息挂到**后来重创的同名新行**上。老消息保持两列 `NULL`、走哈希兜底，观感与今天一致。
- ⚠ **判定「灰临时」只看 `sender_color = 'gray'`**，绝不把 `NULL`（改造前的老消息）当成灰。

## 8. 颜色：逻辑色 ID 入库，显示色由客户端算（16 色 + 灰）

- 池子（**逻辑色 ID，顺序即分配优先级**）：`color_01` `#5E35B1` / 02 `#3949AB` / 03 `#1E88E5` / 04 `#039BE5` / 05 `#00897B` / 06 `#43A047` / 07 `#7CB342` / 08 `#C0CA33` / 09 `#F9A825` / 10 `#FB8C00` / 11 `#F4511E` / 12 `#E53935` / 13 `#D81B60` / 14 `#8E24AA` / 15 `#6D4C41` / 16 `#546E7A`。
- **灰 `gray`（基色 `#8A8A8A`）不在池里**，只给本地临时昵称；**池满（16 条活跃）时新建 → 503 `NO_AVAILABLE_COLOR`，绝不重色**。
- ★ **逻辑色 / 显示色分离**：库里 / 协议里 / 广播里 / 快照里**只有逻辑色 ID**；显示色（含主题变体）**由客户端渲染时算**，**不进协议、不进库** —— NAS 不需要为浅色 / 深色各存一套色，而「昵称颜色是全局统一的」这个概念也不受影响。
- **四条渲染规则**：① 圆点按主题取变体（浅 `mix(base,#000,35%)` / 深 `mix(base,#FFF,30%)`）；② 头像底优先原色，字色自适应（白字 ≥4.5 用白字，否则 0.7 黑字）；③ 两头都不达标的 5 个色（`03/05/06/11/12`）→ 头像底 `mix(base,#000,18%)` + 白字；④ **下拉项不用色值当字色**（改「色块 + 常规字色」）。
- ★ **客户端映射表（PC / Web 两端各实现一份，必须完全一致；「对比」列 = 浅色圆点 / 深色圆点 / 头像底↔字）**：

| 逻辑色 ID | 基础色值 | 浅色圆点（35% 黑） | 深色圆点（30% 白） | 头像底 | 头像字色 | 对比 |
|---|---|---|---|---|---|---|
{TBL}

- **判据**：两个圆点 ≥ **3.0**、头像底↔字 ≥ **4.5** → **16 色 + 灰 全部达标**；`gray` 走同一条规则，不设特例。
- **未知逻辑色 ID**（脏数据 / 比 `pool_version` 更新的 ID）→ 走灰兜底，**绝不把收到的字符串直接塞进 CSS**。

## 11. 风险与坑

1. **不做回填**：老消息靠哈希兜底；回填会把老消息误挂到「重创的同名新行」上（§7）。
2. **`NULL` 二义性**：灰临时消息是 `'gray'`、改造前的老消息是 `NULL` —— 判错会让所有老消息集体变灰。
3. **「当前昵称」在客户端本地**：同一个人的两台浏览器要各选一次；清掉浏览器数据就回到灰色「默认用户」。
4. **昵称被删时正在用它的人**：客户端收到 `nickname_removed` 必须清空本地选用、**回退灰临时**并提示；服务端对已删昵称的写入返回 `409 NICKNAME_INACTIVE`。
5. **同名只有一行 + 颜色上限 16**：两台机器同名 = 用同一条昵称（再建同名只会 409，引导「选用」）；活跃数受颜色唯一性约束，池满时新增失败（503），界面要提前提示。
6. **离线不能改昵称**：UI 必须禁用入口 + 说明原因，否则用户会以为功能坏了。
7. **历史冻结**：改名或改色后旧消息仍显示当时的样子（连颜色也是当时的逻辑色）——「同一个人前后两种颜色」是忠实的历史，不是 bug。
8. **两端映射表要同步改**：逻辑色 → 显示色的规则在 PC 与 Web 各有一份实现，改一处必须同时改另一处（否则「网页端一个色、PC 弹窗另一个色」）。
